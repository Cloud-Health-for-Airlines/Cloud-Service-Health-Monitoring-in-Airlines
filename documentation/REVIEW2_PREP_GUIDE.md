## 3. Every step explained, in the order of the walkthrough

### Step 1: Real flights (BTS On-Time Performance)
- **What it is:** the U.S. Department of Transportation records every domestic flight: scheduled and actual time, delay minutes and cause, cancelled yes/no. It's public domain.
- **What we downloaded:**
  - December 2022: 557k flights in total, including 116,229 Southwest flights of which 17,000 were cancelled.
  - July 2024: about 640k flights.
- **What we do with it:**
  1. Count flights per minute per airline.
  2. Find disruption days automatically. For each airline we take the median daily cancellation rate and its spread (MAD). A day is flagged if it's more than 3 robust standard deviations above normal **and** above 5%. Consecutive flagged days are merged.
- **Result (say these numbers):**
  - Southwest: 22–29 Dec 2022, peak **77.5%** of flights cancelled vs a normal 0.27%, **16,435** cancellations.
  - Delta: 19–23 Jul 2024, peak **47.4%**, **5,737** cancellations.
  - Nobody hand-labelled these. The code found them in raw government data.
- **Why it matters:** this is our real **ground truth**. Delta and United recovered by 26 Dec but Southwest kept failing until the 29th. That is the IT/crew-scheduling part of the story.

### Step 2: Real bookings (BTS DB1B)
- **What it is:** a 10% random sample of all real airline tickets sold in the U.S., with origin, destination, airline, passengers and fare. This is the real "airline booking dataset". Real booking records are confidential, and DB1B is the best public substitute.
- **What we do:** total passengers per airline for the quarter × 10, divided by that airline's number of departures. That gives **booked journeys per departure**: Southwest 88.2, Delta 105.1, American 113.3, United 118.9.
- **Likely question:** "A 737 has 175 seats; why only 88?" DB1B counts each *journey* once, not each flight leg. A passenger flying A→B→C is one journey but sits on two flights. For the booking system a journey is one booking, so 88 is the right number for bookings. It undercounts per-flight check-in and baggage; this is listed as a limitation.

### Step 3: Real cloud traffic shape (Azure Functions 2019)
- **What it is:** Microsoft published per-minute request counts of real production serverless functions for 14 days. This is the "Azure dataset" (Azure Public Dataset).
- **What we do:** take the 400 busiest HTTP functions (HTTP = user-facing APIs, like booking). Keep the 202 that clearly have a day/night pattern, because machine traffic is flat over the day while human traffic is not. From those we extract:
  1. **Diurnal profile:** demand by minute of day. Peak-to-trough is 3.5×; busiest at 14:00 UTC, quietest at 03:00.
  2. **Burstiness:** how much traffic jumps minute to minute around its trend. We average 16 real functions to mimic many users.
- **Why:** real users don't arrive at a constant rate. Before, we used a constant 45 rps plus random noise.
- **Weakness:** the data is in UTC from an unknown region, so we use only its *shape*.

### Step 4: Real cluster behaviour (Alibaba 2022 microservices trace)
- **What it is:** Alibaba published 13 days of CPU and memory use for the machines running its production microservices. This is the "cluster workload dataset".
- **What we use:** 1,000 machines × 12 hours = 708k one-minute samples. **Median CPU 18.5%**, p90 32%, p99 55%.
- **Meaning:** real clouds keep a lot of spare capacity and autoscale. We set our autoscaler's target utilisation from this (0.40).
- **The key point of the project:** the cloud can scale; the mainframe behind it cannot. That mismatch is the research gap.

### Step 5: Real cloud failures (Google Cloud Service Health)
- **What it is:** Google publishes every incident on its status page: start, end, affected products, severity. This is the "cloud service health dataset".
- **The problem we solved:** the live feed now keeps only about 7 months (7 incidents). We merged yearly snapshots saved by the Internet Archive to recover **902 incidents, Dec 2020 to 2026**.
- **What we use:**
  - Fault-type mix. A keyword classifier on descriptions gives: connection failures 63%, network latency 26%, batch/queue stalls 11%.
  - Severity mix: low 56%, medium 36%, high 9%.
  - Duration distribution: median 3.2 h.
- **Two honest adjustments:**
  1. Real incidents are rare (about 13 a month across *all* of Google Cloud), so we **oversample frequency** (one fault per ~8 h) to have enough cascade examples.
  2. Incident durations are long-tailed (p90 is 36 h, because that's Google's whole incident), so we **cap** them at 4 h, assuming the airline fails over by then.
  Types, severities and the shape of durations stay real.

### Step 6: Generating reservation workload (the reviewer's term)
This is how real airline activity becomes IT requests per second. Each line is one request stream:

| Stream | Formula | Served by |
|---|---|---|
| Bookings | (daily passengers = departures × 88.2) spread over the day by the Azure profile | cloud → **mainframe** (3 calls: create PNR, price, ticket) |
| Searches | bookings × **1,000** (look-to-book ratio) | cloud **cache** only (never reaches the mainframe) |
| Check-in | each flown flight's passengers: 60% online in the 24 h–1 h before departure, 40% at the airport 3 h–40 min before | cloud → mainframe (2 calls) |
| Baggage | passengers × 0.7 bags × 3 scans, in the 2 h before departure | cloud (10% to mainframe) |
| Crew | 5 crew per flight × 2 roster checks; **plus**, for each cancelled or delayed flight, 5 crew × 12 re-planning operations | cloud → mainframe |
| Rebooking | passengers of cancelled flights, spread over 6 h before to 1 h after | cloud → mainframe (6 calls each) |

Real example from the walkthrough (Southwest, 14:00–15:00):

|   | Normal day (14 Dec) | Meltdown day (26 Dec) |
|---|---|---|
| Flights scheduled | 228 | 214 (179 cancelled) |
| Searches | 5,663 rps | 5,960 rps |
| Check-in | 4.2 rps | 0.7 rps (cancelled flights don't check in) |
| Rebooking | 0 | 4.8 rps |
| Crew | 1.7 rps | 4.1 rps |
| **Mainframe load** | **28 rps** | **52 rps** |
| Mainframe capacity | 41 rps | 41 rps |

Over the whole meltdown, sustained mainframe load was **1.47×** normal.

- **Mainframe capacity:** 1.25 × the 99th-percentile load on normal days. The mainframe is sized for normal peaks plus 25%.
- **Look-to-book source:** Amadeus reported about 1,000:1; OAG says 10,000–20,000:1 now (PhocusWire articles).
- **Which numbers are assumptions?** The multipliers (3, 2, 6, 12, 0.7). We tested how sensitive the conclusion is to them (`results/real_data/sensitivity.md`). With rebooking at 2–4 calls per passenger, demand alone almost never exceeds capacity. From 6–8 calls, it does for hours during the meltdown.

### How the cloud manages that workload (the reviewer's term)
- **Caching:** searches (1000× bookings) are answered from a cloud cache, so the mainframe never sees them.
- **Autoscaling:** every 3 minutes each cloud service sets its replicas to demand ÷ (replica capacity × 0.40). Scale-out lags demand, so short bursts cause brief cloud-side slowdowns. We label those as **not** a cascade; they are "hard negatives".
- **Retries:** a failed call to the mainframe is retried up to 2 times. That hides small failure rates (10% loss becomes 0.1%) but multiplies load on big ones (1 + d + d²). This is **retry amplification**.
- **What the cloud cannot do:** scale the mainframe. Autoscaling actually pushes *more* traffic into it.

### Step 7: Simulating the hybrid stack (what is simulated)
- The five services (reservations, crew, baggage, boundary gateway, legacy core) are **simulated** in **10-second steps** for the whole month (per-minute demand is interpolated), using standard queueing rules:
  - **Little's law:** the gateway has a fixed pool of connections to the mainframe, so capacity = connections ÷ time per call. If each call takes 515 ms instead of 15 ms, capacity drops from 43 to about 12 rps.
  - **Gateway queue:** queue(t+1) = queue + arrivals − served. Above a 30-second buffer, requests are rejected. Requests waiting longer than 3 s time out.
  - **Cloud service delay:** grows like 1/(1−utilisation) (the M/M/1 queueing factor).
  - **Drift ε(t):** the gap between what the cloud submits (Φ) and what the mainframe completes (Ψ), plus queue, latency and error terms. Range 8.5–99.5%. The dashboard warns at 45% and marks critical at 70%.
- **How faults develop:** 70% worsen gradually over 2–20 minutes (like incidents that begin as "elevated latency"); 30% are abrupt (hardware or data-centre failures, like Alaska Airlines 2025). The split is our assumption. Fault strength rises linearly from 0 to its full level over the ramp.
- **Cascade label (exact definition):** reservations are degraded (error ≥ 10% or latency ≥ 150 ms) **and** the boundary is degraded (gateway error ≥ 5% or latency ≥ 100 ms), **for at least 30 seconds**. Both must hold, so a pure cloud-side slowdown doesn't count, and one noisy 10-second reading doesn't either.
- **Episodes:** we cut 60-minute windows: 500 per airline, half with a cascade and half without. Among the negatives we deliberately include "hard negatives" (a fault or a cloud slowdown that did *not* become a cascade), so the model can't learn "fault means cascade".
- **Lead time:** time from the first warning sign in the window (fault start, or mainframe demand above capacity) to the cascade. Median **3 minutes**, mean 11 min, range 10 s to ~1 h.
- **Dataset:** 1,000 episodes, 500 cascades. 391 cascades are fault-driven and 109 are pure demand surges (mostly Southwest meltdown days).
- **What the walkthrough example shows (6 Dec 2022, 12:12):** a medium network fault that grows gradually.
  - For 3.5 minutes, gateway latency climbs 15 → 136 ms and drift 8.5 → 32%, while capacity is still above demand. **That is the warning window.**
  - At 12:15:30, bookings wait over 150 ms end-to-end and the cascade starts.
  - Then capacity (connections ÷ latency) falls toward demand.
  The cloud side did nothing wrong; the boundary choked.

## 4. Results, and how to explain each number

Event split: trained on **Southwest Dec-2022** (400 train + 100 validation episodes), tested on **Delta Jul-2024** (500 episodes the model never saw).

| Model | Early warning AUC / F1 | Detection AUC / F1 |
|---|---|---|
| BACCP hetero-RGCN | **0.625 / 0.554** | 0.870 / 0.829 |
| Logistic regression | 0.589 / 0.524 | **0.911 / 0.847** |
| Drift rule (ε ≥ 45%) | 0.595 / 0.047 | 0.855 / 0.804 |

External check on real Train-Ticket telemetry (RCAEval), zero-shot:
- detection weights: AUC **0.82**, but they catch only 28% of cascades at the 0.5 threshold;
- early-warning weights: AUC **0.20**, meaning their ranking is backwards on that system (it does not transfer).

Leakage check (same 2-minute task, simple models):

| Split | AUC |
|---|---|
| Random split inside Southwest | 0.96 |
| Split by day inside Southwest | 0.67 |
| Southwest → Delta | 0.61 |

**What the terms mean (expect to be asked):**
- **Precision:** of the alarms we raised, how many were real cascades.
- **Recall:** of the real cascades, how many we caught.
- **F1:** the balance of the two.
- **AUC:** the probability that the model scores a random cascade window higher than a random normal window. 0.5 is a coin flip; 1.0 is perfect. AUC doesn't depend on the alarm threshold; F1 does.
- **Early warning:** the model sees only snapshots from before (cascade time − 2 min). Normal windows are cut at matching random times, so window length can't give the answer away.
- **Detection:** the model sees the whole hour, including after the cascade started.

**How to explain the results:**
1. **Detection works on an unseen airline (0.87–0.91)**, but logistic regression matches or beats the graph model. So far, the graph structure doesn't add much on this data. Say it plainly.
2. **Early warning is the open problem.** BACCP ranks best (0.63), but every model is close to chance. The drift rule almost never fires in time.
3. **Why early warning is hard (know this cold):**
   - After the 10-second upgrade, only **54%** of cascades show *any* sign 2 minutes before they start; abrupt faults and fast ramps give none.
   - Early in a ramp, a fault that will cascade and a fault that will fizzle look alike.
   - Accuracy drops as you look further ahead (simple models: ~0.72 at 30 s, ~0.60 at 2 min).
   - For instant failures, only fast *detection plus automatic mitigation* helps, which is what the circuit-breaker part of BACCP is for.
4. **The leakage check is our strongest methods point.** Random split 0.96 vs split by day 0.67, on the same data. The model was "remembering" the same fault from overlapping windows. Our old 0.96 synthetic result used a random split, which is why it can't be trusted.
5. **RCAEval:** the detection model transfers to a real microservice system (AUC 0.82) without retraining; the early-warning model does not (0.20). Thresholds must be recalibrated for any new system.
6. **0.96 → 0.6–0.9** is the honest gap between synthetic and real data. This is the strongest argument that her advice was right.

## 5. Question bank (with answers)

### Gap and motivation
1. **"What is your research gap, in one line?"** Nobody links real airline operational demand to the health of the hybrid cloud-plus-legacy IT stack, or predicts the cascades that start at the boundary between them. And nobody tests such a predictor on a different airline and event.
2. **"How did you find the gap?"** We compared three areas: cloud AIOps (cloud-only data), airline operations research (treats IT as reliable), and incident reports (Southwest 2022, Delta 2024, Alaska 2025). Each covers one part; none connects operations to IT failure. Then we checked with real data: Alibaba's cloud runs at 18% CPU (lots of headroom), while the Southwest meltdown pushed sustained mainframe load to 1.47× normal.
3. **"Why is the boundary the problem?"** The cloud autoscales; the mainframe has fixed capacity. During a surge, the cloud scales out and forwards even more writes into a system that cannot grow.
4. **"Is the Southwest meltdown really an IT problem?"** The storm was the trigger. Southwest's executives and the pilots' union both cite the crew-scheduling system (SkySolver) being overwhelmed. Our BTS data agrees: other airlines recovered by 26 Dec, Southwest only by the 29th/30th.
5. **"What exactly is new in your work?"**
   - The trace-driven dataset that joins airline operations data with cloud traces and incident statistics.
   - A generation-typed graph (cloud / gateway / legacy) instead of a flat cloud graph.
   - Testing on a different airline and real event.
   - An early-warning evaluation, not just detection.

### Data
6. **"Is this real data or AI data?"** The inputs are real: flights, tickets, cloud traffic, cluster utilisation, incidents. The airline services are simulated, because no airline publishes internal telemetry and you can't break a real airline's systems on purpose. This approach is called *trace-driven simulation* and is standard in systems research.
7. **"Why not Kaggle airline booking datasets?"** The EaseMyTrip one is real but needs a login and covers only Indian routes; it could add a booking-lead-time curve later. The British Airways `customer_booking.csv` comes from a job simulation and its origin isn't documented, so we didn't use it as "real".
8. **"Why Google Cloud incidents and not AWS or Azure?"** Google publishes structured JSON with start, end, severity and products. AWS and Azure only give about 90 days of RSS. We recovered 902 Google incidents through the Internet Archive.
9. **"Why Alibaba and not Google Borg?"** Alibaba's 2022 trace is about *microservices* (like our cloud tier) and downloads directly. Google's 2019 trace is 2.4 TB and only available through BigQuery; we documented a sample query.
10. **"Can I verify your data?"** Yes. `download.py --list` shows every URL. `download.py` re-downloads everything, and `prepare.py` reprocesses it. The tests check the Southwest and Delta windows directly.
11. **"How big is it?"** About 1.2 GB raw (not in git), 3 MB processed (in git), 1,000 training episodes.

### Workload and cloud
12. **"What is look-to-book?"** Searches per booking. Amadeus reported about 1,000:1; OAG now says 10,000+. Searches go to the cloud cache, so the exact value doesn't change mainframe load.
13. **"Where do 6 calls per rebooking and 12 crew operations come from?"** They're assumptions; real per-transaction numbers are not public. We tested 2–10 and reported how the conclusion changes (`sensitivity.md`). Say plainly: "This is an assumption, and here is how sensitive the result is to it."
14. **"How did you decide mainframe capacity?"** 1.25 × the 99th percentile of normal-day demand, meaning sized for normal peaks plus 25%. We also tested 1.1 and 1.5.
15. **"What is autoscaling here?"** Every 3 minutes, replicas = demand ÷ (replica capacity × target). The target (0.40) comes from Alibaba's real utilisation.

### Simulation and labels
16. **"How do you label a cascade?"** Reservations degraded (error ≥ 10% or latency ≥ 150 ms) **and** the boundary degraded (gateway error ≥ 5% or latency ≥ 100 ms). Cloud-only slowdowns are counted as negatives.
17. **"Why oversample faults?"** Real Google incidents happen about 13 a month across all of Google Cloud. A single airline boundary would see very few, which is too few cascades to learn from. We kept the real types, severities and duration shape, and changed only the frequency.
18. **"Why cap durations at 4 hours?"** Google's durations cover their entire incident (p90 = 36 h). An airline would fail over long before that.
19. **"What is ε(t)?"** Drift: (cloud submissions − mainframe completions) ÷ submissions, plus queue, latency and error terms, on a 0–100% scale. Warning at 45%, critical at 70%.
20. **"What is Little's law?"** Items in a system = arrival rate × time each spends there. With a fixed connection pool, throughput = connections ÷ latency, so slower calls mean lower capacity.

### Model and results
21. **"Why is your accuracy lower than before?"** Before, we trained and tested on data from our own equations, so the model learned our equations. Now it's tested on a different airline and real event. Lower is honest, and it shows the synthetic number was inflated.
22. **"Logistic regression beats your model at detection. So why a GNN?"** Honest answer: on this data, with 400 training episodes and one airline to learn from, the graph model doesn't yet beat a linear model on detection (0.87 vs 0.91). It ranks slightly better on early warning (0.63 vs 0.59), but both are near chance. We report this instead of hiding it. The GNN's expected advantage is on bigger, more varied topologies. Testing that needs more airline-months and real multi-service telemetry like RCAEval; there, a GNN trained on RCAEval did better on "which faults spread" (0.83 vs 0.75).
23. **"What is an event split, and why not a random split?"** A random split puts near-identical windows from the same days into both train and test, which inflates scores. An event split tests on a completely different airline and disruption.
24. **"What is AUC?"** See §4: the chance a cascade window scores higher than a normal one. 0.5 is random.
25. **"What does zero-shot on RCAEval mean?"** We took weights trained on our Southwest data and ran them on a different, real microservice system (Train-Ticket) without retraining. The detection model got AUC 0.82; the early-warning model got 0.20 (backwards), so it does not transfer.
26. **"What is lead time and how accurate is it?"** Time from the first warning sign to the cascade: median 3 min, range 10 s to ~1 h. Our lead-time error is about 7 minutes (MAE ≈ 410 s), which is larger than the typical lead time, so the lead-time head is **not usable yet**. Say so.
26b. **"Why 10-second steps and gradual faults?"** At 1-minute steps, almost every fault broke the system within one step, so there was nothing to predict. Real incidents often start as 'elevated latency' and get worse. We made 70% of faults ramp up over 2–20 min (an assumption) and kept 30% abrupt.
26c. **"What is data leakage?"** When the test set contains information the model already saw in training. Our overlapping 60-minute windows from the same fault leaked under a random split (0.96); splitting by day removes it (0.67).
27. **"What is a heterogeneous / relational GCN?"** A graph neural network where nodes have types (cloud, gateway, legacy) and each edge type (cloud→gateway, gateway→legacy, …) has its own weights. A flat GCN treats every connection the same.

### Honesty and process
28. **"Did you use AI to build this?"** Answer honestly. Yes, we used AI coding assistants to write code faster. The research decisions, the dataset choices, the checks on the data (for example, the disruption windows match the real news events) and the honest reporting of weak results are ours, and we can explain every step. Then offer to run the walkthrough live.
29. **"What are the limitations?"**
    - Simulated services.
    - Assumed per-passenger multipliers and fault ramp shapes.
    - Per-minute demand interpolated to 10 s, so sub-minute bursts are smoothed.
    - UTC traffic shape.
    - DB1B counts journeys, not flight legs.
    - Oversampled faults.
    - One random seed and two airline-months.
    - Lead-time head not yet accurate.
30. **"What's next?"**
    1. Better early warning: longer history per sample, trend features, and per-airline normalisation.
    2. More months, including the Alaska Airlines October 2025 outage (`download.py bts_ontime --param year=2025 month=10`).
    3. Recalibrate thresholds per system.
    4. Connect the RL circuit breaker to the real-data workload.

## 7. Do not say

- "Our model is 96% accurate." (Synthetic only.)
- "We predict every cascade 18 seconds in advance." (We predict about 2 minutes ahead and only weakly.)
- "The GNN beats the baselines." (Not on detection with this data.)

## 9. Quick glossary

| Term | Meaning |
|---|---|
| Workload / cluster trace | Real log of jobs and resource usage from a production cluster (Google Borg, Alibaba, Azure) |
| Azure Public Dataset | Microsoft's real anonymised Azure traces (VMs, Functions, …) |
| BTS / TranStats | U.S. government transport statistics: On-Time, DB1B, T-100 |
| DB1B | 10% sample of real U.S. airline tickets |
| Trace-driven simulation | Simulator fed by real recorded inputs |
| Ground truth | Verified real labels (our BTS disruption windows) |
| Look-to-book | Searches per booking |
| Autoscaling | Adding or removing servers automatically based on load |
| Retry amplification | Retries multiply load during failures |
| Little's law | L = λW; fixed connections ⇒ throughput = connections ÷ latency |
| Hard negative | A case that looks risky but didn't fail; it teaches the model the difference |
| Data leakage | Test data containing information the model saw in training (e.g. overlapping windows of one fault) |
| Fault ramp | A fault that grows from 0 to full strength over minutes instead of hitting at once |
| Event split | Test on a different real event than the one trained on |
| Zero-shot | Applying a trained model to a new system without retraining |
| AUC / F1 | Ranking quality / balance of precision and recall |
| Conformal prediction | Turns a score into an interval with a guaranteed coverage rate (e.g. 90%) |
